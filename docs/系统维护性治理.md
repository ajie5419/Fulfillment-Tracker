# 系统维护性治理

本轮治理覆盖部门身份、权限与通知、计划分流、设计与工艺联动、采购数量、上传限制、预警阈值及桌面/手机状态显示。演示环境和生产环境使用同一份业务代码；数据库、登录来源和演示工具由环境配置隔离。代码提交不代表生产已部署。

## 以后在哪里修改

| 变更需求 | 唯一维护入口 | 必须保持的行为 |
| --- | --- | --- |
| 部门显示名称 | `shared/business-depts.ts` 的 `BUSINESS_DEPT_NAME` | 编码不变，权限、通知接收人不变；历史名称映射保持兼容 |
| 通知角色文字 | `shared/notify-roles.ts` | 数据库角色编码不变 |
| 待办动作文字 | `shared/todo-actions.ts` | 现有待办继续按稳定动作码执行 |
| 节点是否进入工艺 | 模板或实例的 `requiresProcess` | 节点改名不改变分流；模板修改不追改已有实例 |
| 采购数量及精度 | `shared/purchase-quantity.ts` | 表单、接口和 Excel 导入一致，不能存入舍入为零的数量 |
| 上传大小或文件数 | `shared/upload-policy.ts` | 校验和提示同步变化，请求体上限保留 multipart 开销 |
| 预警提醒单位及阈值关系 | `shared/alert-policy.ts` | 设置界面与服务端校验一致；存储单位仍为小时 |
| 设计任务接口字段 | 服务端响应及 `ClientResponse` | 页面类型自动跟随，禁止重新手写 `DrawingRow` 等副本 |
| 客户确认状态 | `shared/drawing.ts` | 桌面列表、看板和手机端使用相同业务判断 |

共享规则不负责颜色、排版和控件选择，各端只做视觉适配。外部 QMS 部门名称在接入边界转换为内部部门编码，未知历史值保留并在设置页提示待映射，不猜测其权限。

## 工艺联动约束

`PlanTemplateNode` 和 `PlanNode` 分别保存 `requiresProcess`。生成计划时复制属性，未挂节点的独立设计任务默认需要工艺。新建节点也默认需要工艺，采购计划、调试等节点由模板或编辑人明确关闭。

工艺列表、工艺写操作、车间开工校验、采购齐套和设计变更处理读取相同策略。策略切换、设计任务改挂、删除节点和替换模板通过 `server/services/process/requirements.ts` 同步开工待办及工艺提醒，不等待下一次扫描修补。

事务按工件→设计任务→计划节点顺序加锁；关联在等待期间变化时回滚并提示刷新。恢复工艺要求时，原已下发文档转为“修改中”并记录操作者和复核原因；未开始的文档保持原状态。这样可以复核关闭期间发生的图纸变更。历史变更提醒只按当前料单修改轮次恢复，已完成的旧轮次不能重新弹出。

## 历史数据升级

- `20261110150000_stable_department_identity`：将负责人配置中的七种已知部门名称转换为稳定编码，保留未知值、空值和其他角色。
- `20261110151000_explicit_process_routing`：新增工艺要求属性；只在这次迁移中依据历史节点名称回填采购计划及“调试”为关闭，其余为开启。运行时不再按名称判断。
- 改模板只影响之后生成的计划；已有计划属性需按实例调整。
- 升级验证应从旧版结构和非空历史数据开始，核对负责人、节点、日期、发布状态、确认记录及前置关系，并重复部署确认没有二次变化。
- 回退旧代码不能只换程序：旧代码仍按中文部门身份查询，而且不认识明确的工艺属性。生产回退需配套数据恢复方案；优先保留新结构并修正代码，不在运行中直接反向改写角色配置。
- 若停写后反向转换部门数据，升级记录不会随之撤销；再次升级时必须显式重新归一部门身份，`migrate deploy` 不会重跑已经执行过的转换。

## 防止再次分散

`pnpm quality:check` 同时检查原有质量计数和新增架构约束。新增约束没有基线豁免，包括前端导入服务端运行时代码、已治理响应模型被重新手写、工艺分流重新依赖名称、权限使用显示字典、采购限制及上传提示再次写死。

这些是针对已发现问题的规则，不是通用语义分析。新的业务规则仍需审查归属和行为回归；新增一种重复方式时，应同时补可复现用例和检查。不能把提高基线当作通过方式。

CI 保留类型检查、单元测试、构建和独立 MySQL 集成测试。`REQUIRE_TEST_DATABASE=1` 确保数据库缺失会失败，而不是全部跳过后显示成功。测试库名称必须含独立的 `test` 分段；集成测试会清表，禁止指向演示或生产库。

每批改动按功能边界独立本地提交。验收分别记录源码检查、单元测试、真实 MySQL、历史升级、桌面/手机运行检查；静态检查通过不能代替运行验收，演示验证也不能代替生产部署验收。
