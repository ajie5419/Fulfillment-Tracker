# 风险与项目总览重叠收拾、项目全景：第一阶段交接

本阶段仅修改服务端、shared 逻辑和测试，没有修改 `.vue`、菜单、页面、数据库结构、W 系列阈值、预警扫描写入逻辑或异常状态机。

## 1. 超期异常对拍与统一

基线：`036b238`。

先纠正现状描述中的一点：`issues.ts` 的 `overdue` 原本取实时 `judgeW4().level` 是否非空，并不是取扫描写入的级别。扫描写入的级别在独立字段 `alertLevel` 中返回；两者不能互相替代。

`judgeW4` 的原始行为保持不变：

- 仅关注 `OPEN`、`ACCEPTED`；`RESOLVED`、`CLOSED` 返回级别为空、时长与天数为零。
- `OPEN` 自创建起累计达到 `W4.yellowDays` 天时变黄；待受理再久也不会单凭待受理时长变红。
- `OPEN`、`ACCEPTED` 超过要求解决日达到黄阈值时变黄，达到红阈值时变红；优先取红。
- 待受理时长和解决日超期天数都扣除停工日，以北京时间计算日界；解决日当天不算超期。没有解决日，`overdueDays` 为零。
- `level` 是实时计算结果；扫描写入的预警还受原有“只升不降”机制影响。

原消费方的差异：

| 样本（默认黄 1 天、红 3 天） | 原异常列表 `overdue` | 原看板 / 总览超期计数 | 原看板异常颜色输入 | 统一后 |
| --- | --- | --- | --- | --- |
| 待受理超过黄阈值，解决日未过或未填 | 是，天数 0 | 不计 | 黄 | 计为超期，天数仍为 0，黄 |
| 待受理 / 处理中，解决日已过 1–2 个计时日 | 是 | 计 | 黄 | 相同 |
| 解决日已过红阈值 | 是 | 计 | 红 | 相同 |
| 待确认 / 已关闭，即使解决日已过 | 否 | 不计 | 无 | 相同 |
| 两者皆未超 | 否 | 不计 | 无 | 相同 |
| 将黄阈值设为 2 天，处理中已过解决日 1 个计时日 | **否** | **计** | 黄 | 计为超期，天数 1，黄 |

唯一只读实现为 `server/services/issues/overdue.ts` 的 `judgeIssueOverdue`：

> 待受理满 W4 黄阈值，或待受理 / 处理中已过要求解决日，即为超期；待确认、已关闭不算。

沿用现有北京时间及停工日算法。因此，解决日之后如果全部是停工日，超期天数仍为 0，不单凭日历日期已经过去就计超期。

输出 `{ overdue, overdueDays, color }`。`overdueDays` 专指解决日超期天数，不把待受理时长换成这个字段；`color` 是看板的实时异常颜色输入，不是持久化 `alertLevel`。

已接入：异常列表和详情、看板每单 `overdueIssues` / `overdueCount` 及红黄输入、总览 `summary.overdueIssues` / `stages.issue` / `byDept.overdue`、驾驶舱超期数字及清单。工单详情原本复用异常列表，因此同步生效。

数字影响面：

- 看板每单、总览总数与部门超期数补计“单纯待受理超时”，不再漏掉 `overdueDays = 0` 的真实超期异常；相应工单原因文字、胶囊和详情总数也会变化。
- 自定义黄阈值大于 1 时，异常列表补计“已过解决日、尚未到黄阈值”的样本；驾驶舱清单也补计这类样本。
- 原看板红黄判定已包含上述两类，因此现有有效阈值下，这次只是让计数与其颜色输入统一，不主动改变原红黄绿结果。
- 各接口原有权限和工单筛选范围保留；比较总数仍须使用相同可见范围和工单状态范围。
- 没有修改 `judgeW4`、`scan.ts`、阈值、扫描写入或状态迁移。统一无需改变持久化 `alertLevel` 的含义；实时超期与扫描级别可因配置、扫描时间或只升不降机制而不同。

## 2. 红色清单分组契约

`shared/board-cockpit.ts`：

- `mergeCockpitItems` 按 `workOrderNumber` 分组，一单一行；行 `key` 固定为 `wo:<工单号>`。
- 主类型优先级：`workOrder`（红色工单）→ `issue`（超期异常）→ `stagnation`（停滞红线）。同类型选自身天数最大的一项为主项，同天数按原事项 key 稳定选择。
- 保留 `kind`、`label`、`title`、`detail`、`responsibility`、`duration`、`days`、`to`、可选 `workOrder` 等主要字段。
- 新增必有字段 `also: CockpitConcern[]`，包含主项以外的全部问题，含同类型的其他异常、其他停滞对象。每项保留自己的 `key`、`kind`、`label`、`title`、`detail`、`duration`、`days`、`responsibility`、`to`，可直接逐项进入原详情。
- 行 `days` 用于排序，取该单已知的解决日超期、停滞、预计拖期的最大天数；红色工单的停滞摘要和正值 `delayDays` 也参与。负拖期不当成超期时长。
- 主项 `duration` 保留对应时钟的说明；红色工单行会说明最大值来源（异常超期 / 已停 / **预计**拖期）。`also[].days` 始终是该问题自身的天数。
- 待受理超时但 `overdueDays = 0` 的异常仍入列，显示“待受理超时”，未知天数为 `null`，不编造已过解决日天数。
- 先排主类型，再排该单最大天数降序，最后按工单 key 稳定排序；完成分组、排序后截取 10 **单**。

第二阶段前端需展示 `also` 并更新清单帮助文案。现有 `.vue` 尚未渲染附加项，本阶段严格未改呈现。

另一个必要接入点：当前 `BoardCockpit.vue` 传的是 `/api/monitoring/status.top`（先按对象取前 10）。去重后，10 个对象可能属于同一工单；此数据不足以保证选出前 10 个不同工单，也无法保全该单所有停滞附加项。第二阶段应通过现有 `/api/monitoring/entities?level=RED&page=…&pageSize=…` 分页取得完整红线候选，再传给合并函数。不能拿 Top 长度代替红线总数。

## 3. GET /api/panorama

接口命名按需求保留，响应类型在 `shared/panorama.ts` 的 `PanoramaData`。无需查询参数。

权限与 `/api/board` 一致：要求登录，使用 `getScope → scopeWorkOrders`；项目经理受限于自己的工单，领导 / 管理员等沿用既有 actor 范围，没有另加领导专属限制。

服务直接调用 `getBoard(visibleWorkOrders, now, { withClosed: true })`，全景没有第二套红黄绿算法。看板行新增可选业务数据对应的 `productLine: string | null`，来源为 `WorkOrderExt.productLine`。

`counts`：

| 字段 | 口径 |
| --- | --- |
| `inProgress` | 状态严格等于 `IN_PROGRESS` |
| `normal` | 在制且看板色为 `GREEN` |
| `abnormal` | 在制且看板色为 `RED` / `YELLOW` |
| `completed` | 状态严格等于 `COMPLETED` |
| `notStarted` | 状态严格等于 `OPEN`；页面应以小字说明“未开工” |
| `unaccepted` | 恒为 `null`，没有数据来源 |
| `unacceptedAvailable` | 恒为 `false`，与 `unaccepted` 同在 `counts` 内 |

`normal + abnormal = inProgress`。删除、取消及未约定的其他状态不计入上述数字，也不产生分组。未验收不得显示为零、不得用 `OPEN` 或其他数字倒推。

- `byManager[]`：`{ projectManagerId: string | null, projectManagerName: string, inProgress: number, abnormal: number }`。按 ID 分组，重名不合并；无经理时 ID 为 `null`、姓名为“未指定项目经理”；已设置 ID 但用户名称不可得时沿用看板的 ID 回退。
- `byProductLine[]`：`{ productLine: string | null, inProgress: number, abnormal: number }`。`null` 表示未指定，前端可显示“未指定产品线”。
- 分组成员来自当前可见的在制、未开工、已完工工单；后两者只建立分组，不增加分组的在制 / 异常数字。因此仅有已完工项目的经理可能出现 0 / 0。
- 两组都按在制数降序、异常数降序，再按名称 / ID 稳定排序；分组在制数、异常数之和分别等于对应总数。
- 没有数据时返回零计数、空数组，并仍保留 `unaccepted: null` / `unacceptedAvailable: false`。
