## 1. 计划完成的锁后校验（10.1）

文件：`server/services/plan/commands.ts`、`queries.ts`、`loaders.ts`、`server/services/kitting/kitting.ts`；`tests/unit/plan-completion-lock.test.ts`、`tests/integration/plan.test.ts` 及计划服务快照。

原流程在事务外读取子节点、计算是否完成，随后只锁节点再写手动完成。`createNode`、`updateNode`、`deleteNode` 在 `commands.ts` 中先锁计划行，因此原校验与写入之间可新增子节点。`tasks.ts#createPlanTask` 创建的是挂靠的部门任务，不是子节点，当前没有取得计划锁；本批不改变部门任务的锁协议。

新流程仅用首次定位读取获取工单号，然后在同一事务内按现有结构变更顺序取得 **计划行 → 节点行** 锁，重读子节点，用同一事务加载完整计划并计算完成条件。空子节点集合也在计划锁后读取。`loadPlans/loadPlanSources/loadKitCounts` 增加可选事务客户端，普通调用默认仍用 prisma；预测的节点和业务事实不使用锁前快照。名称加载只影响展示，保留现有批量查询方式。

单测固定锁序及“锁前无子节点、锁后新增未完成子节点”必须拒绝；集成测试通过查询扩展屏障，在完成流程定位读之后、计划锁之前用另一个真实事务创建子节点，验证父节点不能手动完成。

## 3. 分页契约及消费方盘点（10.3）

### 兼容策略

旧页面的 useFetch 直接从原 URL 推导数组类型，且风险页、驾驶舱同时用全量数组做统计。为同时满足本批不改 app/、双 typecheck 和优先兼容，**新增规范分页 URL，保留旧 URL 作为兼容入口**。分页服务以 PageResult 为唯一返回契约；旧端点需由前端工坊切换后再移除。不是把旧数组改成只含第一页而继续冒充全量。

所有新分页入口都复用 `shared/pagination.ts` 的 PageResult、默认 50、最大 100 及 Zod 分页字段/偏移校验。原 `server/schemas/pagination.ts` 仅转出共享定义，既有采购入口继续兼容。

### 查询实现与稳定排序

文件：`server/services/releases/queries.ts`、`issues/queries.ts`、新增 `issues/paging.ts`、`plan/list.ts`、`comments/comments.ts`、新增五个 GET handler、`shared/pagination.ts` 及 server schema 转出。

- 发放、留言、项目计划明细均以数据库 skip/take 与 count 实现，名称/预测仅装配当前页。发放不再硬截 200。
- 异常分页不读取全部异常再切片：以三个互斥条件桶实现原排序（超期 → 其余未关闭 → 已关闭），分别 count，计算落在各桶的 skip/take，最多装配 pageSize 条。待办权限转为数据库条件，并对照原 issuePermissions 测试。超期条件反求现有 judgeIssueOverdue 的单调时间边界，不另写停工日算法；覆盖自定义阈值、停工日、毫秒边界、空 dueDate。SQL 的 dueDate 条件显式排除 null，保证 NOT 桶的三值逻辑不会漏行。
- 发放：`createdAt DESC, id DESC`；留言：`createdAt ASC, id ASC`；异常：桶顺序 + `createdAt DESC, id DESC`；计划：`deliveryDate ASC, workOrderNumber ASC`。在固定数据集下跨页不重不漏。offset 分页不承诺跨多次请求期间仍冻结并发新增/删除的数据快照。
- 全量异常入口也增加 id 兜底排序，保持与分页顺序一致。

### 规模判断

无生产数据库访问，本批不虚构实际记录量。源码显示发放已碰到 200 硬上限风险；异常的 500 仅是读取批量，无总量上限；计划按可见在做工单增长；留言单对象内容最多 1000 字、但条数无上限。因此四者都提供真正分页的页面入口。项目预测的节点/挂靠任务属于完整图计算，不能按列表页大小截断。

## 4. QMS 本地保存恢复（10.2）

文件：`prisma/schema.prisma`、增量 migration、新增 `server/services/workorder/recovery.ts`、修改 `manage.ts`、`sync/write-client.ts`、`schemas/work-order.ts`、工单 POST/PUT handler；新增管理员 retry handler、`shared/work-order-save.ts`；恢复/客户端/既有管理单测和新增恢复集成测试。

新增表 `work_order_local_save`，包括唯一 operationId、工单号、create/update、actorId、扩展字段 JSON、远端请求 JSON、远端结果/明确拒绝 JSON、PENDING/DONE、尝试次数、最后错误、创建/更新时间和完成时间。另设可空唯一 pendingWorkOrder：同工单最多一条 PENDING，DONE 置空，保留历史幂等标识。无外键绑定本地工单副本，创建前也能存意图；migration 只加此表，不修改旧表。

1. 校验权限、人员及当前可判断的约束后，先独立提交 PENDING 意图；未成功落库就不调用 QMS。客户端不传 key 时由服务端生成，兼容旧调用；推荐前端主动生成并复用 key。
2. 对恢复记录 FOR UPDATE，串行处理同 key；验证同 key 的工单、操作人、操作类型、远端请求、扩展输入严格相同。不同输入不能借原 key 覆盖。
3. 尝试次数先独立持久化（防外层回滚/进程中断抹去已调用远端的证据），然后首次调用 QMS；远端成功后保存响应，再在独立本地事务中写副本和本次扩展输入。成功标 DONE 并释放 pendingWorkOrder。
4. 本地事务失败时回滚副本与扩展字段，外层记录保留 PENDING、尝试数、最后错误、远端结果；接口返回 202 + recovery。即使此时状态更新也遇数据库故障，调用远端前的 PENDING 仍存在，并返回已确认远端成功/本地待恢复。
5. 重试函数 `retryWorkOrderSave` 挂到现有风格的 defineAdminHandler 设置路径。每次重试先核对 QMS 的工单现状：已记录远端成功就补本地，不再 create/update；响应丢失时必须匹配本次请求，新建有同号但输入不符或修改版本无法判定时保留 PENDING 报待核对，不盲目重发。管理员重试即使 attempts 为 0 也先核对；已 DONE 再调直接返回原结果，不再次写远端。
6. QMS 明确拒绝时将记录终止为 DONE，保存 remoteError，释放工单的新意图；同 key 重放同一拒绝。网络错误/结果未知仍保留 PENDING。仅改本地扩展字段不调用 QMS，若已有 PENDING 会先拒绝这次扩展修改。

QMS 现有文档只约定了增量分页读取，没有按工单号的 GET。本批 findWorkOrder 沿现有 `/api/integration/fulfillment/work-orders` 同步契约分页查找，未假造新的远端端点；不看后台同步开关，使用相同身份凭据。查找失败必须抛错，不得当作不存在来再次创建。代价是恢复核对可能扫描多页；恢复事务设置具名超时，超时保留 PENDING 可再次调用。现有 QMS 成功响应仍是本地副本唯一来源，不从前端构造远端副本。

本批只给 create/update 的扩展输入加恢复协议，取消工单不带扩展输入，保留原取消流程。未增加后台轮询、通用任务队列或跨系统补偿框架。对未知远端结果保守保留输入；需要管理员核对的冲突不自动认领别人的同号工单。
