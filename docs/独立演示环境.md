# 独立演示环境

此启动方式使用本机 Kiri 中的独立 `ft-demo-mysql` 容器（MySQL 8.0，仅映射 `127.0.0.1:13307`），单独创建 `fulfillment_demo` 数据库和仅可访问该库的同名账号。不加载项目 `.env`，不连接原 Apple Container 的 QMS 数据库。

先打开 Kiri。启动脚本优先使用 `/Applications/Kiri.app` 自带的 Docker CLI，并明确连接 Kiri socket；不依赖系统默认 Docker context，也不读取旧 Docker Desktop 的凭据配置。首次启动会拉取 MySQL 镜像并创建专用持久卷 `ft-demo-mysql-data`。已有容器必须通过用途标签和本机端口校验；遇到遗留同名卷不会自动接管或清空。

从 Apple Container 切换的已有数据需先停止旧演示应用，单独备份并导入 `fulfillment_demo`，核对表和记录数后，再使用 `pnpm demo --keep-data`。启动脚本不会自动搬迁旧数据；原 QMS 容器和旧演示库可保留作回退。不要直接把原 MySQL 数据目录挂到新容器。

执行 `pnpm demo --keep-data` 即可构建并启动，无需先在 Mac 上运行 `pnpm build`。启动器通过同一份 `Dockerfile` 的 `local` 阶段，在 Linux/Node 22 容器中安装依赖、生成 Prisma、构建 Nuxt 前后端，再通过 `docker-compose.demo.yml` 启动 `ft-demo-app`。正式生产仍使用精简的 `runtime` 阶段，演示工具不会进入生产镜像。

首次没有数据时可执行 `pnpm demo` 写入样例。已有容器可用 `node scripts/demo.mjs --check` 检查证书及 MySQL 连通性（不创建容器或写数据库）。需要已有 `certs/localhost.pem` 与配套私钥，证书应覆盖 `127.0.0.1`；仅在运行时只读挂载，不进入镜像。Compose 使用显式文件及空环境文件，不自动读取项目 `.env`。

- 演示入口：`https://127.0.0.1:3101`。使用不同于原环境 `localhost` 的主机名，避免两套环境的登录 Cookie 相互覆盖。
- 模拟身份桥：`http://127.0.0.1:4101`，只在本机监听，不连接真实 QMS，不提供同步资源。
- 初始数据：3 个 `DEMO-` 工单及设计、采购、生产、齐套、总计划等演示记录。原来的 113 个工单及试编计划不进入此库。
- 登录时选择岗位；“演示管理员 / 分管领导”（u-005）有管理员权限。换角色使用页面上的退出 / 切换账号入口。
- 附件继续挂载原 `.data/demo/uploads`，重建应用容器不会丢失。数据库连接和身份桥凭据每次启动随机生成，经进程环境传给 Docker，不写入仓库配置或命令参数；容器环境中保存运行所需凭据，避免公开完整 inspect 输出。
- 重启保留试用进度。恢复初始演示数据时，在演示入口的“演示工具”先清除演示数据，再写入演示数据；此操作只针对独立演示库。
- 清除时保留演示登录账号、部门、部门对照和负责人配置，清空业务数据后仍可按岗位编制、发布和接收新计划。
- 启动时补齐旧版本清除操作遗失的身份配置，并为已发布计划中尚未接收、未完成的非汇总节点补建缺失接收待办；重复启动不会重复发待办，不修改原计划日期、基线或接收状态。此修复仅由独立演示启动脚本执行，不影响生产环境。
- 启动命令在容器健康后返回，关闭终端不会停止服务。执行 `pnpm demo --stop` 可停止应用与模拟身份桥，数据库及附件保留；Kiri 中停止 `ft-demo-app` 效果相同。不要并发启动两份命令。由旧宿主机服务切换时须先停止旧 LaunchAgent/Node 进程，释放 3101/4101 端口。

在“项目总览”点击“新建工单”，工单号使用 `DEMO-` 前缀（例如 `DEMO-WO-004`），选择演示客户、填写数量和交期。保存后可编制项目计划；工单详情支持修改和取消。新建、修改、取消仅写入独立演示库，不连接真实 QMS，仍按项目部或管理员权限控制。新建工单也纳入演示数据清理范围。

模拟身份桥只承担角色登录。不要将此入口作为正式业务环境使用。
# 合同生效日期

总计划在草稿阶段不计算执行延期或上游延期传播，总计划表不显示“预计／完成”列；过去的计划日期仅提示发布前核对。发布后才按当前日期与实际执行情况预测。此规则由生产和演示共用。

总计划概览显示工单号和 QMS 的 `effectiveTime`（合同生效日期）；缺失时显示“—”。上线需先部署 QMS 同步字段，执行履约数据库迁移，再重拉历史工单以补齐该字段。

更新已有演示环境时使用 `pnpm demo --keep-data`，迁移数据库并保留当前数据，不重新写入演示样例。

## Docker 全容器测试

直接运行 `pnpm test:kiri`。前后端构建、质量门禁、类型检查、全部单元测试、迁移与集成测试均在 Docker 内执行。登录集成测试也在容器内启动真实 Nuxt 构建产物，覆盖桌面/手机 HTML、JavaScript 静态资源、登录及 API；浏览器交互仍需另做实际验收。

每次运行使用随机命名的 Compose 项目，包含独立测试执行容器、MySQL、内部网络和临时数据卷；不发布测试数据库端口、不挂载宿主机 node_modules、不连接演示库，也不连接真实 QMS。凭据临时随机生成，测试固定开启 `REQUIRE_TEST_DATABASE=1`，缺库不能跳过。成功、失败或正常中断后自动删除本轮容器、网络和临时卷，不留下常驻测试数据库；构建缓存保留供下次复用。强制杀死启动器后如有残留，只清理对应的 `ft-test-<随机编号>` 项目。旧版 `ft-test-mysql` 不再被新命令使用。

单工单沙盒 `scripts/sandbox.mjs` 仍是独立的旧 Apple Container 流程；其已有配置和数据不由上述命令迁移。
