## B：transport 与全部迁移点位

实现位于 `app/utils/transport.ts`，端点类型在 `app/types/client-api.ts`。响应通过 type-only 端点导入与 Nitro Serialize 取得，body/query 通过原有 zod schema 的 input 类型取得；端点就近只导出 RequestBody/RequestQuery 类型，没有运行时导入、DTO 搬迁或 schema 修改。

`clientRequest` 绑定 URL、HTTP 方法、body/query 与响应类型，调用者不能指定返回 DTO。`sendClientRequest` 仅供领域重载实现使用，返回 unknown；具体领域函数仍保留原名，并在公开签名校验端点契约。底层只负责发送和归一错误，不含业务判断。

原来使用 useRequestFetch 的地方继续在 setup 捕获并传入，SSR cookie/header 转发机制保留。signal、headers、请求 key、并发控制及上传顺序保留；取消错误保持原身份。usePagedList 仅把读取依赖改为领域注入，分页积累、失效、重试及竞态逻辑不变。

错误文案顺序保持 `data.message → data.statusMessage → error.message → 操作失败`；统一错误包含 statusCode/statusMessage/message/data，C 部分另加入可读 code。

## C：稳定错误码

| code | HTTP |
| --- | --- |
| NOT_FOUND | 404 |
| VALIDATION | 400 |
| CONFLICT | 409 |
| INTERNAL | 保留原 HTTP 状态，例如 QMS 不可用仍为 503 |

唯一码表与 HTTP 映射在 `shared/errors.ts`。FlowError/FlowHttpError 可携带 code，API 仍使用 H3 的 createError；只在原响应中新增 `data.code`，保留 statusCode/statusMessage/message。未携带 code 的旧 FlowError、FlowForbidden、FlowHttpError 与未知异常保持原来的通道和 HTTP 行为。

`server/services/issues/issues.ts` 的详情、写操作 guard、加备注三处“异常不存在”统一携带 NOT_FOUND，详情原 400 改为 404。`server/services/workorder/manage.ts` 本地工单不存在保留 404 并加 NOT_FOUND。异常的状态冲突与并发写冲突使用 CONFLICT；描述/照片校验、API 的 body/query/ID 校验使用 VALIDATION。

QmsRejected 原有 code 供服务层识别，保持不变；API 边界把它按既有 HTTP 状态适配为最小业务码。QmsUnavailable 使用 INTERNAL，仍返回 503。客户端同时支持 error.code、error.data.code 与 H3/ofetch 实际嵌套的 error.data.data.code；没有 code 时文案继续走旧逻辑。
