# 第 4 批：共享纯规则与拆环

本批按「只搬家、不变义」执行。根目录 AGENTS.md、CLAUDE.md 和前端设计规范已读取；没有安装依赖、修改数据库 schema、变更 API 形状或业务阈值，也没有 commit / push。

## A：日期语义与兼容入口

唯一实现模块为 `shared/dates.ts`。原 flow/dates、alerts/rules、plan/constants、mobile-todo 和 useFlow 入口保留兼容导出。

| 原实现 / 调用方 | 原有语义 | 共享函数及保留的区别 |
| --- | --- | --- |
| flow/dates.parseDay；计划日期解析 | 日期字段表示哪一天，存为该日 UTC 零点 | `parseDay`，不按上海或浏览器时区换日 |
| alerts.dateFieldDay；计划 / 齐套的计划日、承诺日、需求日 | 从日期字段取 ISO 前 10 位 | `dateFieldDay`，不把日期字段当本地时刻 |
| flow/dates.todayDay；生产调度、在制、在外、待办 | `Intl` 按 Asia/Shanghai 取自然日 | `todayDay` 调用 `factoryDay`；保留历史时区规则 |
| mobile-todo.factoryDay；待办截止日和页面日期 | `Intl` 工厂日；纯日期字符串原样返回；可指定其他时区 | `factoryDay`，三个行为全部保留 |
| alerts.shanghaiDay / shanghaiDayStart；预警、监控 residenceDays、齐套记录完成时刻 | 固定 UTC+8 的自然日 / 零点毫秒数 | 保留同名函数；不与历史 `Intl` 上海日期强行合并 |
| plan/constants.addDays、mobile-todo.addDays | UTC 日期字符串加日历天，正负天数均支持 | 合并为 `addDays`，月末、年末、闰年行为相同 |
| W1/W2/W5 等计时；停工日时长扣除 | 经过毫秒数，扣除固定 UTC+8 整天的交集 | `elapsedExcludingOffDays`，仍区分经过时长和自然日差 |
| useFlow.dayAfter；登记默认日期、快捷日期、页面当天比较 | 当前时刻经过 n×24 小时，再取运行环境本地日期 | `localDayAfter`，旧名 re-export；没有改成上海自然日或本地日历加天 |

区别例子：`2026-12-31T16:00:00Z` 的 UTC 日期字段是 12-31，上海日是 01-01；上海零点前后一毫秒只经过一毫秒，自然日差却是一天。1990 年夏季 `Intl` 上海日期与固定 UTC+8 可能相差一天。纽约夏令时转换时，经过 24 小时可能跳过一个日期或仍在同一天。

`shared-dates.test.ts` 覆盖这些区别、跨 UTC 零点、月末 / 年末 / 闰年加天、逾期归零、停工日边界和旧入口函数身份。

## B：计划校验

`shared/plan-validation.ts` 包含：

- `isPlanStartLate`：开始日期字段晚于完成日期字段才非法；同日合法，未选日期不报这条错误。
- `planAdjustmentNeedsReason`：发布后新增 / 删除要原因；编辑时仅完成日改变要原因，未提供新日期不算改变。
- `isPlanAdjustmentReasonMissing`：需要原因时，空值和全空白不合法。

PlanEditor 的即时提示、提交检查与 plan.ts 的最终拒绝共用上述函数。Dayjs 到日期字符串的适配留在前端，并保留无效 Dayjs 的原 `isAfter` 结果。阶段分组、日期显示、开始日 / 部门等其他字段变化的政策不变。前端通用提示和服务端含具体日期 / 动作的中文错误消息分别保持原文。

先用真实组件 computed 和真实服务私有校验钉版，搬移后在同一组用例中同时验证共享函数及两端适配；未复制一份生产算法作为测试 oracle。

## C：权限差异表

| 输入 / 规则 | 前端原行为 | 服务端原行为 | 本批处理 |
| --- | --- | --- | --- |
| 管理员、部门员工 / 负责人、项目部负责人等基准角色 | 使用 `/api/me` 的 `can` 标志 | `permissionFlags` 调用 `canOperate` | 本来就同源，继续由服务端计算 |
| purchase / payment / route / plan 的本工单项目经理 | `pmOf` 数组包含目标工单 | `pmOf` Set 包含目标工单 | 共用 `isProjectManagerOf`；不改变操作集合 |
| stepAction 的本人负责人 | 非空 ownerId 等于本人 ID | 相同 | 共用 `isObjectOwner` |
| 班组长的自制开工 / 完工 / 报工 | leaderAction + SELF + 本班组 | 接口先按操作种类及 SELF 筛 teamId，再判断班组 | 共用 `leaderTeamOfStep`、`leadsTeam`，前端组合为 `canLeadStepAction`；门控位置不变 |
| 工艺部发放 | 通用 release 按钮可见；另有 releaseProcessOnly 标志 | 目标 DRAWING / CHANGE 拒绝，PROCESS 放行 | 有意保留：入口显示不能代替目标文件类型校验 |
| 报检关联多个工单 | canDo 仅接收一个 workOrderNumber | 任意 workOrderNumbers 中的项目经理均可 | 有意保留：后端支持多工单目标；没有扩大前端输入 |
| canDoAny 列表新建 / 导入按钮 | 只要是任意工单项目经理就显示 | 对具体对象仍判断所属工单 | 有意保留：列表可操作可能性不等于具体对象授权 |

共享纯谓词位于 `shared/permissions.ts`；没有把前端显示逻辑和服务端授权强行对齐。新增对照表覆盖普通用户、项目经理、部门负责人、项目部负责人、管理员、负责人、班组长、外协和非班组长操作。

可见范围实现实际原位于 `server/utils/auth.ts`，不是 permissions.ts。已最小搬移为 `server/services/auth/scope.ts`：`Scope`、`resolveScope`、`canSee`、`scopeWorkOrders`；auth.ts 保留导出与按请求缓存包装，事务 db 参数及查询保持不变。

## E：循环依赖

原依赖两端均为运行时函数：auth.ts 为角色上下文加载引用 responsible.ts 的 `teamsLedBy`；responsible.ts 为班组长工单范围检查引用 auth.ts 的 `resolveScope` / `canSee`。
