# 项目履约系统上线手册

适用：首次上线，履约系统与 QMS 同一台 ECS，数据库用 QMS 同一个阿里云 RDS MySQL 实例（单独建库、单独账号）。

本手册只写步骤，不会自动执行任何东西。每一步都有：**做什么 → 怎么确认 → 出问题怎么回滚**。按顺序做，上一步确认通过再做下一步。

## 0. 准备

### 0.1 先填好这张表（不要把真实值写进仓库或聊天记录）

| 占位符 | 含义 | 例子 |
|---|---|---|
| `<IP>` | ECS 公网 IP（用户浏览器访问的地址） | `47.x.x.x` |
| `<RDS_HOST>` | RDS **内网**连接地址 | `rm-xxxx.mysql.rds.aliyuncs.com` |
| `<DB_PASS>` | 履约库专用账号密码（新生成） | — |
| `<CLIENT_SECRET>` | 身份桥客户端密钥（新生成，两边相同） | — |
| `<ADMIN_IDS>` | 履约系统管理员的 QMS 用户 ID，逗号分隔 | 第 5.5 步查 |
| `<OPS_EMAIL>` | 证书到期通知邮箱 | — |

生成密钥（在自己电脑或 ECS 上执行，结果只填进两边的 env 文件）：

```bash
openssl rand -hex 32   # <CLIENT_SECRET>，64 位，满足 ≥32 位要求
openssl rand -hex 16   # <DB_PASS>，只含字母数字，放进连接串不用转义
```

### 0.2 端口与网络约定

| 端口 | 归属 | 本次是否改动 |
|---|---|---|
| 80 | QMS 前端容器 `qms-frontend` | **不动**。证书不走 80 端口验证，也不要在 80 上加任何东西 |
| 443 | 新增：Caddy（证书 + 反向代理） | 新开，安全组放行入方向 TCP 443 |
| 8443 | 推荐新增：Caddy → QMS 的 HTTPS 入口（3.5，待负责人确认） | 采用时安全组放行入方向 TCP 8443 |
| 127.0.0.1:3000 | QMS 后端 | 不动 |
| 127.0.0.1:3100 | 履约系统容器 `fulfillment` | 新增，只绑本机 |

履约容器加入 QMS 已有的 docker 网络 `qms-network`，服务端经 `http://qms-backend:3000` 调 QMS（身份桥 + 只读同步接口）。浏览器登录时跳转到 QMS 授权页，登录后回到 `https://<IP>/auth/callback`。授权页推荐走 HTTPS（`https://<IP>:8443/#/identity/authorize`，见 3.5，待负责人确认）；备选是现状的 `http://<IP>/#/identity/authorize`，**QMS 密码明文传输**。

上线前检查：

```bash
ss -ltnp | grep -E ':(80|443|3000|3100)\b'   # 80 属于 docker-proxy（QMS），443 和 3100 应当空闲
docker network ls | grep qms-network          # QMS 网络存在
```

## 1. 先部署 QMS（含数据库迁移）

履约系统依赖 QMS 的身份桥、只读同步接口和"项目履约"菜单，这些在 QMS 侧是新版本代码 + 新迁移（身份桥表、同步接口用的复合索引）。

### 1.1 发布 QMS 新版本

1. 在 GitHub 仓库 Quality-Guardian → Settings → Secrets and variables → Actions → **Variables** 新增 `VITE_FULFILLMENT_URL` = `https://<IP>`。前端镜像构建时读取它，菜单"项目履约"才会出现；不设则菜单隐藏，其他不受影响。
2. 按 QMS 仓库 `docs/release-workflow.md` 的正常流程发布：功能 PR 合并 → release PR 合并 → `qgs-v*` tag → `deploy` workflow。迁移由发布执行器在旧后端在线时执行（`prisma migrate deploy`），失败会自动恢复旧 compose 配置。
3. 确认发布的版本至少包含：身份桥、履约只读同步接口、统一登录页、"项目履约"菜单入口。

确认：

```bash
gh run list --workflow deploy.yml --limit 3          # 最新一次 deploy 结论为 success
curl -s http://127.0.0.1:3000/api/status             # 在 ECS 上执行，QMS 后端正常
```

### 1.2 配置 QMS 身份桥（服务端环境变量）

编辑 ECS 上 QMS 的 `.env.production`（与 QMS 的 compose 文件同目录：通常是 `/opt/qms/docker-compose.yml`，部署脚本的备选位置是 `/opt/qms/infra/docker/docker-compose.yml`，下面的命令按实际位置执行；改之前先备份 `cp .env.production .env.production.bak-$(date +%F)`），追加：

```ini
QMS_IDENTITY_CLIENT_ID=fulfillment
QMS_IDENTITY_CLIENT_SECRET=<CLIENT_SECRET>
QMS_IDENTITY_CALLBACK=https://<IP>/auth/callback
# 可选，登录页显示的系统名，默认"项目履约"
# QMS_IDENTITY_CLIENT_NAME=项目履约
```

回调地址必须是 https，不能带 `?` 或 `#`，并且要和履约系统的 `NUXT_QMS_CALLBACK_URL` **一字不差**。

让后端读到新变量（只重建 backend，不动 frontend 和 80 端口）：

```bash
cd /opt/qms
docker compose -f docker-compose.yml up -d --no-deps backend
```

确认（在 ECS 上执行；密钥用 `read -s` 输入，不进 shell 历史）：

```bash
# 登录页名称接口：client id 与回调都对上时返回 {"name":"项目履约"}，否则固定 404
curl -s "http://127.0.0.1:3000/api/identity-bridge/client?clientId=fulfillment&redirectUri=https%3A%2F%2F<IP>%2Fauth%2Fcallback"

# 同步接口：返回 code 0 和 items；401 = 密钥不对，503 = QMS 没读到身份桥变量
read -s S && curl -s -H "X-Identity-Client-Id: fulfillment" -H "X-Identity-Client-Secret: $S" \
  "http://127.0.0.1:3000/api/integration/fulfillment/work-orders?limit=1" | head -c 300; unset S
```

回滚：
- 版本有问题：按 QMS `docs/release-workflow.md` 的回滚流程处理（用 deploy workflow 重新部署上一版本）。本次迁移只新增表和索引，旧版本可以在新库结构上运行，**不要手动回退表结构**。
- 只想关掉对接：把 `.env.production` 恢复为备份，再执行一次 `docker compose -f docker-compose.yml up -d --no-deps backend`。身份桥未配置时一律拒绝（503/404），QMS 本身不受影响。
- 菜单入口：删除仓库变量 `VITE_FULFILLMENT_URL` 后下次发布即隐藏。

## 2. 在阿里云 RDS 上建履约库和专用账号

在 RDS 控制台操作（推荐，不需要高权限账号的密码落到 ECS 上）：

1. 实例 → **数据库管理** → 创建数据库：名称 `fulfillment`，字符集 `utf8mb4`。
2. 实例 → **账号管理** → 创建账号：类型"普通账号"，账号名 `fulfillment`，密码 `<DB_PASS>`；授权数据库只选 `fulfillment`，权限选"读写（DDL + DML）"（迁移要建表）。
3. **白名单**：ECS 内网 IP 已在 QMS 用的白名单里就不用改；没有就加上 ECS 的内网 IP（不要加 `0.0.0.0/0`）。

也可以用高权限账号执行等价 SQL（DMS 里执行即可）：

```sql
CREATE DATABASE IF NOT EXISTS fulfillment DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'fulfillment'@'%' IDENTIFIED BY '<DB_PASS>';
GRANT ALL PRIVILEGES ON `fulfillment`.* TO 'fulfillment'@'%';
```

确认（在 ECS 上，用一次性的 mysql 客户端容器，密码交互输入）：

```bash
docker run --rm -it mysql:8.4 mysql -h <RDS_HOST> -u fulfillment -p -e "SHOW DATABASES; SHOW GRANTS;"
# 只看到 fulfillment（和 information_schema 等系统库），看不到 QMS 的库
```

回滚：控制台删除账号 `fulfillment` 和数据库 `fulfillment`（此时还没有数据）。QMS 的库和账号不受影响。

## 3. Let's Encrypt IP 证书（tls-alpn-01，443 端口）

为什么这样做：
- 没有域名，只能申请 **IP 证书**。Let's Encrypt 的 IP 证书只发短期证书（`shortlived` 配置，有效期约 6 天，≈160 小时），**必须自动续期**，不能手工。
- 验证方式只能用 http-01（80 端口）或 tls-alpn-01（443 端口）。80 端口归 QMS，不能动，所以用 **tls-alpn-01**。
- certbot 不支持 tls-alpn-01，所以用 **Caddy**：它自己在 443 上完成验证、自动续期（剩约 1/3 有效期时续）、同时做反向代理，一个容器解决第 3、4 步。

### 3.1 安全组

ECS 安全组入方向放行 TCP 443，来源 `0.0.0.0/0`（Let's Encrypt 从多个地区回连验证，限制来源会签发失败）。

### 3.2 Caddy 配置

```bash
mkdir -p /opt/caddy && cd /opt/caddy
```

`/opt/caddy/Caddyfile`：

```caddyfile
{
	email <OPS_EMAIL>
	# 不做 80 → 443 跳转，不碰 80 端口
	auto_https disable_redirects
}

<IP> {
	tls {
		issuer acme {
			# 第一次必须先用 Let's Encrypt 测试环境（staging）签发，见 3.3；测通后删掉这一行换正式证书
			dir https://acme-staging-v02.api.letsencrypt.org/directory
			profile shortlived
			disable_http_challenge
		}
	}

	# 上传照片上限：应用一次最多 3 张 × 8MB + 64KB 表单开销 ≈ 24.1MiB（server/api/uploads.post.ts），
	# 入口放到 26MiB，超出的由应用自己返回"照片太大"的 413 提示
	request_body {
		max_size 26MiB
	}

	reverse_proxy 127.0.0.1:3100
}
```

`/opt/caddy/docker-compose.yml`：

```yaml
services:
  caddy:
    image: caddy:2.11.7   # 固定这个版本：2.10.x 带的 acmez 对 IPv4 IP 证书的 tls-alpn-01 验证有问题，2.11.7 已带修复（acmez v3.1.7 / certmagic v0.25.6）
    container_name: caddy
    restart: unless-stopped
    network_mode: host    # 直接监听 443，并能访问只绑 127.0.0.1 的 3100
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data  # 证书和 ACME 账号，必须持久化，否则每次重启都重新申请
      - caddy_config:/config

volumes:
  caddy_data:
  caddy_config:
```

### 3.3 启动

分两步，**测试环境签发成功之前不要切正式环境**。`caddy validate` 只检查配置文件语法，**不会**真的去 Let's Encrypt 申请证书，不能代替下面的测试签发。

第一步：测试环境（Caddyfile 里 `dir https://acme-staging-v02...` 那一行保留）

```bash
cd /opt/caddy
docker compose run --rm caddy caddy validate --config /etc/caddy/Caddyfile   # 只校验语法
docker compose up -d
docker logs -f caddy    # 看到 "certificate obtained successfully" 且 issuer 含 acme-staging 即成功；Ctrl+C 退出
echo | openssl s_client -connect <IP>:443 2>/dev/null | openssl x509 -noout -issuer -ext subjectAltName
# issuer 含 "(STAGING)"，subjectAltName 是 IP Address:<IP>。浏览器会提示不受信任，这是正常的
```

测试签发失败时看 `docker logs caddy` 里的报错（常见：安全组没放行 443、443 被别的程序占用），修好再试；测试环境频率限制宽松，可以反复试。

第二步：正式环境

```bash
cd /opt/caddy
sed -i '/acme-staging-v02/d' Caddyfile    # 删掉测试环境那一行（单文件挂载，改完要重建容器才生效）
docker compose up -d --force-recreate caddy
docker logs -f caddy    # 再次看到 "certificate obtained successfully"（这次是正式环境）
```

确认：

```bash
ss -ltnp | grep -E ':(80|443)\b'
# 443 → caddy；80 仍然 → docker-proxy（QMS），没有 caddy
echo | openssl s_client -connect <IP>:443 2>/dev/null | openssl x509 -noout -issuer -enddate -ext subjectAltName
# issuer 是 Let's Encrypt（不再含 STAGING），subjectAltName 是 IP Address:<IP>，到期时间约 6 天后
curl -s -o /dev/null -w '%{http_code}\n' http://<IP>/   # QMS 首页仍然 200
```

如果日志报 80 端口被占用（个别版本仍会尝试监听 HTTP），在全局块里加一行 `http_port 18080`（不在安全组放行），重新 `docker compose up -d`。**不要**为此停 QMS 前端。

### 3.4 续期监控

Caddy 会自动续期。证书只有约 6 天，续期一旦连续失败很快就会过期，所以加一个每天检查（剩不到 2 天就写系统日志，接入已有告警即可）：

```bash
cat > /etc/cron.daily/check-ip-cert <<'EOF'
#!/bin/sh
echo | openssl s_client -connect 127.0.0.1:443 2>/dev/null | openssl x509 -noout -checkend 172800 >/dev/null \
  || logger -p user.err "fulfillment: 443 certificate expires within 2 days, check: docker logs caddy"
EOF
chmod +x /etc/cron.daily/check-ip-cert
/etc/cron.daily/check-ip-cert && echo ok
```

回滚：`cd /opt/caddy && docker compose down`。443 关闭，履约系统外部无法访问，QMS（80 端口）不受影响。证书数据在卷 `caddy_data` 里，重新 `up -d` 即恢复。

### 3.5 推荐（待负责人确认）：QMS 登录页也走 HTTPS

> ⚠️ **现状**：QMS 目前只有 `http://<IP>`（80 端口，明文）。履约系统登录时会跳到 QMS 登录页输入账号密码，这一步的**密码是明文传输的**，同一网络里的人可以截获。这不是履约系统新引入的问题（QMS 平时登录就是这样），但上线前应当知情并做决定。

推荐做法：用同一个 Caddy、同一张 IP 证书，在 **8443** 端口给 QMS 加一个 HTTPS 入口，履约系统的授权跳转改走这个入口。80 端口保持原样，QMS 用户照常使用旧地址，不受影响。

1. 安全组入方向放行 TCP 8443。
2. `/opt/caddy/Caddyfile` 末尾追加一个站点（证书和 443 上的同一张，不需要再申请）：

```caddyfile
<IP>:8443 {
	tls {
		issuer acme {
			profile shortlived
			disable_http_challenge
		}
	}
	# QMS 前端容器在宿主机 80 端口（它自己再转发 /api 给后端），这里只做 HTTPS 外壳
	reverse_proxy 127.0.0.1:80
}
```

3. `docker compose up -d --force-recreate caddy`，确认：

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://<IP>:8443/   # 200，QMS 首页
curl -s -o /dev/null -w '%{http_code}\n' http://<IP>/          # 仍然 200，旧入口不变
```

浏览器打开 `https://<IP>:8443`，能正常登录 QMS、各页面和上传正常。

4. 履约系统 `.env`（第 5.2 步）改用 HTTPS 授权页：`NUXT_QMS_AUTHORIZE_URL="https://<IP>:8443/#/identity/authorize"`。QMS 仓库变量 `VITE_FULFILLMENT_URL` 不变。`https://<IP>:8443` 和 `http://<IP>` 是两个不同的站点，浏览器里的 QMS 登录状态不共用，用户第一次从履约系统跳过去要再登录一次 QMS，之后正常。

**需要负责人决定的**：是否把 80 端口改为跳转到 `https://<IP>:8443`，或者干脆关闭 80。这会改变全体 QMS 用户的访问地址（收藏夹、二维码、小程序里写死的地址都可能受影响），不在本次上线范围内，本手册不做这一步。

回滚：删掉 Caddyfile 里的 `<IP>:8443` 站点并 `docker compose up -d --force-recreate caddy`，`NUXT_QMS_AUTHORIZE_URL` 改回 `http://<IP>/#/identity/authorize` 后 `docker compose up -d`（在 /opt/fulfillment）。

**不采用时（备选，现状方案）**：授权页继续用 `http://<IP>/#/identity/authorize`，功能完全正常，但要明确：**QMS 账号密码在网络上明文传输**。

## 4. 443 反向代理

已在第 3 步的 Caddyfile 里一并完成：`https://<IP>` → `127.0.0.1:3100`，请求体上限 26MiB。

上限的依据：应用照片上限在代码里是每张 8MB（`server/services/issues/uploads.ts` 的 `MAX_UPLOAD_BYTES`）、一次最多 3 张，`server/api/uploads.post.ts` 的整体上限 = 3 × 8MB + 64KB。入口上限要**略大于**它，超大请求才能到达应用，得到中文的"照片太大"提示，而不是代理层的空白错误页。以后改了应用的照片上限，这里要一起改。

确认：履约容器起来之后（第 5 步），在电脑上传 3 张接近 8MB 的照片能成功；一张超过 8MB 的照片被拒绝并提示"每张照片不能超过 8MB"。

回滚：同第 3 步。

## 5. 部署履约系统（docker compose）

### 5.1 取代码

```bash
mkdir -p /opt/fulfillment && cd /opt/fulfillment
git clone https://github.com/ajie5419/Fulfillment-Tracker.git .
```

之后版本的切换由 GitHub 上的 deploy workflow 自动完成（打 tag 后 SSH 到这台机器执行 `scripts/deploy-remote.sh`，里面会 `git fetch --tags && git checkout <tag>`）；这里不用手动 checkout。

目录名 `fulfillment` 决定 compose 项目名，照片数据卷会叫 `fulfillment_uploads`（第 7 步备份用到）。

### 5.2 环境变量 `/opt/fulfillment/.env`

```bash
cp .env.example .env && chmod 600 .env
```

按下表改成生产值（`.env` 不提交，不要发到聊天里）：

```ini
DATABASE_URL="mysql://fulfillment:<DB_PASS>@<RDS_HOST>:3306/fulfillment"

# 服务端调 QMS：docker-compose.yml 已固定为 http://qms-backend:3000，这里写不写都会被覆盖
NUXT_QMS_API_BASE="http://qms-backend:3000"
# 浏览器跳转的 QMS 授权页（生产是 hash 路由）
# 推荐（做了 3.5 步）：https://<IP>:8443/#/identity/authorize
# 备选（现状，QMS 密码明文传输）：http://<IP>/#/identity/authorize
NUXT_QMS_AUTHORIZE_URL="https://<IP>:8443/#/identity/authorize"
# 与 QMS 的 QMS_IDENTITY_CLIENT_ID / QMS_IDENTITY_CLIENT_SECRET 完全相同
NUXT_QMS_CLIENT_ID="fulfillment"
NUXT_QMS_CLIENT_SECRET="<CLIENT_SECRET>"
# 与 QMS 的 QMS_IDENTITY_CALLBACK 一字不差
NUXT_QMS_CALLBACK_URL="https://<IP>/auth/callback"

# 管理员（设置页：阈值、停工日、通知对象、工单项目经理）。首次上线先留空，5.5 步查到 ID 后再填
NUXT_ADMIN_USER_IDS=""

# 照片目录：容器内路径，docker-compose.yml 已把数据卷挂在这里，重建容器照片不丢
NUXT_UPLOAD_DIR="/app/data/uploads"

# 演示工具：生产必须关闭（不写或写 0）
NUXT_DEV_TOOLS=0
```

同时**删掉** `.env.example` 里带过来的本地开发项：`DEV_HTTPS_KEY`、`DEV_HTTPS_CERT`（生产 https 由 Caddy 负责）。`NUXT_QMS_SYNC_ENABLED` 不写即开启同步。

确认（只看变量名和长度，不打印值）：

```bash
grep -E '^(DATABASE_URL|NUXT_[A-Z_]+)=' .env | cut -d= -f1
awk -F= '/^NUXT_QMS_CLIENT_SECRET=/{gsub(/"/,"",$2); print "secret length:", length($2)}' .env   # ≥ 32
grep -c DEV_HTTPS .env   # 0
```

### 5.3 构建、迁移、启动

首次上线（或 GitHub 上还没配好 Secrets 时）手工执行：

```bash
cd /opt/fulfillment
docker compose build
docker compose run --rm fulfillment prisma migrate deploy   # 必须在启动前执行
docker compose up -d
```

之后每次发版由 deploy workflow 在打 tag 后自动做同样的事（`scripts/deploy-remote.sh`，多了回滚点和健康检查）。手工部署一次之后，ECS 上就有 `fulfillment-tracker:prev` 回滚镜像可用。

确认：

```bash
docker compose ps                                                   # fulfillment 状态 healthy（健康检查约 30 秒一次）
curl -s http://127.0.0.1:3100/api/health                            # {"ok":true}（应用 + 数据库都通）
ss -ltnp | grep 3100                                                # 只有 127.0.0.1:3100
docker network inspect qms-network --format '{{range .Containers}}{{.Name}} {{end}}'   # 含 fulfillment
docker exec fulfillment node -e "fetch('http://qms-backend:3000/api/status').then(r=>console.log(r.status))"   # 200
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' https://<IP>/   # 302，跳到 https://<IP>/auth/login?redirect=%2F
docker logs --tail 50 fulfillment   # 没有缺少环境变量的报错（缺必填项会启动即退出）
```

### 5.4 首次登录与同步

1. 电脑浏览器打开 `https://<IP>/`：证书无警告 → 跳到 QMS 登录页，副标题"登录后进入 项目履约" → 用 QMS 账号登录 → 回到履约系统首页，右上角显示姓名。
2. 等 5 分钟（`sync-qms` 每 5 分钟一轮），或看日志 `docker logs -f fulfillment`。之后查同步状态：

```bash
docker run --rm -it mysql:8.4 mysql -h <RDS_HOST> -u fulfillment -p fulfillment \
  -e "SELECT resource, lastSyncedAt, failCount, LEFT(lastError, 80) err FROM sync_cursor;"
# 7 类资源都有 lastSyncedAt，failCount = 0，err 为空
```

也可以在页面看：看板上的"QMS 最后同步"时间。

### 5.5 设置管理员

同步完成后查管理员的 QMS 用户 ID：

```sql
SELECT id, username, realName FROM qms_user WHERE username IN ('<登录名1>', '<登录名2>');
```

把 ID 填进 `.env` 的 `NUXT_ADMIN_USER_IDS`（逗号分隔），然后 `docker compose up -d`（变了 env 会重建容器）。确认：管理员登录后菜单出现"设置"，其他人没有。

### 5.6 回滚

- 新版本有问题、要回到上一个版本：`scripts/deploy-remote.sh` 每次构建前会把**正在运行**的容器镜像（按镜像 ID，不是 tag）打成 `fulfillment-tracker:prev`，健康检查失败时自动回退。人工回退用 `docker tag fulfillment-tracker:prev fulfillment-tracker:latest && docker compose up -d`。若新版本带了迁移，先评估旧版本能否在新表结构上运行，不行就按第 7 步从备份恢复数据库。
- 首次上线整体撤回：`docker compose down`（**不要**加 `-v`，照片卷保留）。还没正式试点时，可在 RDS 控制台删库重来。
- QMS 不受履约容器停止影响。

## 6. 试点前清除演示数据（DEMO- 前缀）

生产 `NUXT_DEV_TOOLS` 一直关着、从没写过演示数据的话，这一步只做"确认"。

先确认有没有演示数据：

```sql
SELECT 'part' t, COUNT(*) n FROM part WHERE id LIKE 'DEMO-%' OR workOrderNumber LIKE 'DEMO-%'
UNION ALL SELECT 'qms_work_order', COUNT(*) FROM qms_work_order WHERE workOrderNumber LIKE 'DEMO-%'
UNION ALL SELECT 'issue', COUNT(*) FROM issue WHERE workOrderNumber LIKE 'DEMO-%'
UNION ALL SELECT 'qms_supplier', COUNT(*) FROM qms_supplier WHERE id LIKE 'DEMO-%'
UNION ALL SELECT 'qms_process', COUNT(*) FROM qms_process WHERE id LIKE 'DEMO-%'
UNION ALL SELECT 'qms_user', COUNT(*) FROM qms_user WHERE username LIKE 'DEMO-%';
```

全是 0 就跳过。有的话（例如上线前在生产上做过演示培训），用系统自带的清除功能，**不要手写 DELETE**（它会连带清掉引用演示数据的步骤、流转记录、待办、预警、提醒、照片文件）：

1. 选一个没人用的时段。`.env` 临时改 `NUXT_DEV_TOOLS=1`，`docker compose up -d`。
2. 用管理员登录，菜单"演示工具" → "清除演示数据"，记下返回的删除数量。
3. `.env` 改回 `NUXT_DEV_TOOLS=0`，`docker compose up -d`。
4. 重跑上面的 SQL，全部为 0；重新登录后菜单里不再有"演示工具"（关闭后 `/api/dev/*` 一律 404）。

注意：清除会把**阈值恢复为默认**。所以先清演示数据，再让管理员配置阈值、通知对象。从 QMS 同步来的真实数据不会被删（只删 `DEMO-` 开头的）。

回滚：清除不可撤销，只影响演示数据。真要找回，从第 7 步的备份恢复。

## 7. 把履约库加入现有备份

### 7.1 数据库

- RDS 自动备份是**实例级**的，新建的 `fulfillment` 库默认包含在内。到 RDS 控制台 → 备份恢复 → 备份策略，确认已开启、保留天数符合要求；如果备份策略里限定了"备份对象"（库级备份），把 `fulfillment` 加进去。
- 如果现在还有自建的逻辑备份（`mysqldump` 定时任务或 DMS 备份计划），在库列表里加上 `fulfillment`。

### 7.2 照片

照片在 ECS 本地数据卷 `fulfillment_uploads`，**不在**数据库和 OSS 里，要单独备份。每天打包一次（按现有习惯再同步到 OSS 或别的机器）：

```bash
mkdir -p /opt/backup/fulfillment
cat > /etc/cron.daily/backup-fulfillment-uploads <<'EOF'
#!/bin/sh
docker run --rm -v fulfillment_uploads:/data:ro -v /opt/backup/fulfillment:/backup alpine \
  tar czf /backup/uploads-$(date +%F).tgz -C /data .
find /opt/backup/fulfillment -name 'uploads-*.tgz' -mtime +14 -delete
EOF
chmod +x /etc/cron.daily/backup-fulfillment-uploads
```

确认：

```bash
/etc/cron.daily/backup-fulfillment-uploads && ls -lh /opt/backup/fulfillment   # 有当天的包
tar tzf /opt/backup/fulfillment/uploads-$(date +%F).tgz | head                  # 能列出文件
```

RDS 控制台第二天能看到包含 `fulfillment` 的备份记录。

**恢复演练**（试点前做一次）：用 RDS"恢复到新实例/克隆实例"或把逻辑备份导入一个临时库，确认 `fulfillment` 的表和行数都在；照片包解压到临时目录能打开图片。

回滚：删除上面两个 cron 文件即可，不影响业务。
