# 代码质量审查（Fulfillment Tracker，修订合并版）

审查及事实复核日期：2026-10-19。代码基线：`edf8ac4`（合并 R12 齐套功能）。范围：`server/`、`app/`、`tests/`、`scripts/`、Prisma 模型、构建及部署配置。

本文合并原报告和全面审查，删除误判、合并重复项。记录的是尚未整改的问题，不代表已修复。本次修订仅改本文，不改业务代码、数据库、配置或部署状态。

## 一、结论与证据口径

项目采用 Nuxt/Nitro、Prisma 的模块化单体，已有路由校验、事务、行锁、条件更新、唯一键去重和规则单元测试。适合沿当前技术路线继续迭代，没有证据支持拆成微服务或整体重写。

但已确认待办转交越权、异常工件仍计入齐套、停用账号既有会话未撤权，以及前端选择状态和请求顺序问题。类型检查、单测和构建通过不能证明这些业务约束正确。应先处理权限、状态一致性和操作对象正确性，再处理分页、查询放大和模块职责。

不保留“明显高于同类”“主要不是写错”“阻断级问题为零”等缺少比较基准或验收依据的结论。

### 证据等级

- **源码确认**：当前实现存在可定位的缺口，不等于线上已经发生事故。
- **源码沙箱复现**：执行当前源码或实际 Vue 响应式逻辑，数据库、文件或网络使用内存替身；不等于真实 HTTP、MySQL 或浏览器验收。
- **条件性风险**：缺少保护已由源码确认，但是否触发取决于数据量、并发、部署或配置，需额外运行验证。
- **改进建议**：维护性、工程门禁或文档问题，不计为已经发生的业务故障。

P1 表示优先处理的权限、业务完整性或错单风险；P2 表示重要的边界、可靠性和扩展性问题。优先级不替代证据等级，条件性风险仍需保留触发条件。

## 二、已确认缺陷

### F01 / P1：待办转交缺少操作者校验，可扩大特定变更单权限

```ts
export async function transferTodo(todoId: string, toUserId: string)
```

接口和服务未传入当前操作者。服务检查待办开放、目标用户存在、目标不同于原负责人，但没有验证请求者是不是原负责人。知道他人开放待办 ID 的登录用户，可以转交可转交的待办。

影响不只是提醒归属：把 `CONFIRM_CHANGE` 待办转给自己后，发放单相关人判断认可该身份；确认接口也把本人的开放确认待办作为授权依据。源码沙箱执行实际转交、确认及附件读取路径，验证了原本受工单范围限制的用户可以查看相关变更单、读取附件、确认变更并解除等待。待办完成后，相关人资格仍保留。

范围限定：这是特定变更单的权限扩大，不是管理员权限，也不意味着能转交 `SIGN_RELEASE`、代签收或任意作废。现有“签收待办转交返回 400”测试不能证明原负责人校验存在。

建议：转交服务接收操作者，校验原归属、业务范围及目标资格；管理员例外须明确规定。补非本人、跨工单及变更单权限联动测试。

依据：[转交接口](../server/api/todos/[id]/transfer.post.ts)、[转交服务](../server/services/flow/todos.ts)、[发放单相关人与确认授权](../server/services/releases/releases.ts)、[附件授权](../server/services/issues/uploads.ts)、[现有权限测试](../tests/integration/scope-http.test.ts)。

### F02 / P1：末工序不合格后，工件仍可能被计为齐套

```ts
await tx.routeStep.update({ where: { id: step.id }, data: { status: 'BLOCKED' } })
```

```ts
export const isPartReady = (p: { status: PartStatus }) => p.status === 'DONE'
```

末工序足量返厂把工件设为 `DONE`；后续 QMS 不合格扫描只把工序设为 `BLOCKED`，不撤销工件完成状态。齐套直接按工件 `DONE` 计数，并跳过该工件的缺项原因分析。

源码沙箱执行 `recordReturn → syncNonconforming → loadKits`，得到 `part=DONE、step=BLOCKED、ready=1/1、percent=100、shortages=0`；再次扫描没有纠正。实际同步编排同样先匹配返厂、后处理不合格。人工关闭异常时的恢复逻辑不能解决异常仍开放期间的误判。

建议：统一工序异常、工件完成、节点齐套的状态约束，补“不合格发生在末工序足量返厂之后”的跨模块回归测试。

依据：[返厂与阻塞](../server/services/flow/flow.ts)、[不合格扫描](../server/services/issues/nonconforming.ts)、[齐套判定](../server/services/kitting/constants.ts)、[齐套查询及缺项](../server/services/kitting/kitting.ts)、[同步编排](../server/services/sync/job.ts)。

### F03 / P1：停用、删除账号的既有会话仍被接受并续期

```ts
const session = await db.session.findUnique({ where: { id } })
```

认证只核对会话是否存在、是否过期，不复核 QMS 用户的停用、删除状态。用户同步不撤销对应会话，后续权限入口也未补上账号状态检查。

源码沙箱执行实际认证中间件，对 `INACTIVE`、`isDeleted=true` 分别验证，既有未过期会话均被接受并续期，用户表查询次数为零。剩余有效期不足一半时可再续 30 天，持续使用时不能把残留访问能力描述为“最多 30 天”。

范围限定：未过期的既有会话，不是过期会话复活，也未证明停用用户能重新通过 QMS 登录。现有停用用户登录测试不覆盖会话撤权。

建议：定义撤权时效，在请求认证或用户状态同步时落实撤销，测试状态变更前已登录的用户。

依据：[会话解析](../server/services/auth/session.ts)、[认证中间件](../server/middleware/auth.ts)、[用户同步](../server/services/sync/resources.ts)、[登录测试](../tests/integration/login.test.ts)。

### F04 / P1：弹窗保持打开时换对象，可能把 A 的表单保存到 B

```ts
watch(() => props.open, ...)
```

```ts
await purchaseSend(`/api/purchases/${props.line.id}`, 'PATCH', body)
```

采购、图纸编辑弹窗只监听打开状态初始化表单，提交目标却读取当前对象 ID。父页可通过查询参数变化、异步加载替换对象；弹窗仍打开时，表单可能保留 A，提交目标已变为 B。

Vue 响应式及模拟请求验证：保持打开、把 A 换成 B 时串单成立；先关闭 A、再打开 B 正常。不能表述为“正常逐条编辑必然串单”，本次未执行真实业务写入。

建议：表单初始化同时关联记录 ID，固定本次编辑的对象快照，处理父页重叠请求。

依据：[采购弹窗](../app/components/PurchaseEditModal.vue)、[图纸弹窗](../app/components/DrawingEditModal.vue)、[采购父页](../app/pages/purchases.vue)、[图纸父页](../app/pages/drawings.vue)。

### F05 / P1：手机发出页清空工件后，仍可提交隐藏的旧工序

```vue
@click="partId = ''"
```

```ts
const canSubmit = computed(() => !!stepId.value && !!supplierId.value && !!promisedReturnDate.value)
```

“换一个”仅清空工件，旧工序、供应商、日期仍保留，提交条件不检查当前工件和工序归属。Vue 状态模拟验证：没有选中工件时，仍能向旧工序的发出接口提交。

范围限定：发生在清空至重新选定之间；重新选定工件会更新或清空工序，不能写成“选新工件后必然仍发旧工件”。

### F06 / P2：异常列表先截断再筛选，漏掉真正属于当前用户的待办

```ts
const issues = await prisma.issue.findMany({ where, orderBy: [{ createdAt: 'desc' }], take: PAGE_LIMIT })
```

```ts
if (filter.mine === 'todo') rows = rows.filter((r) => r.can.accept || r.can.resolve || r.can.close)
```

最新 500 条之后的记录不再参与“等我处理”和超期筛选。调用实际服务，以模拟数据提供 501 条异常，唯一可由当前用户受理的记录位于第 501 条，接口返回 0 条。

### F07 / P2：发放详情请求乱序，可能显示并操作上一条记录

```ts
detail.value = await fetchRelease(props.id)
```

切换对象没有取消旧请求、请求序号或返回后的 ID 校验。内存模拟按“A 请求、B 请求、B 返回、A 返回”执行，当前选择 B，最终详情却是 A。后续签收、确认、作废从详情读取目标，存在操作错单风险；本次未发送真实写请求。

建议：切换时清理旧详情，使过期请求不能更新当前状态，操作前再次核对对象。

依据：[发放详情抽屉](../app/components/ReleaseDrawer.vue)、[发放父页](../app/pages/releases.vue)。

### F08 / P2：采购列表不能继续读取超出上限的数据

```vue
:pagination="{ pageSize: 50, hideOnSinglePage: true }"
```

采购服务返回最多 500 条及真实 `total`，桌面端只对已加载记录每页显示 50 条，没有服务端翻页或截断提示，手机到货列表也没有继续加载入口。超出上限的记录不能通过翻页访问，需要进一步筛选。

不要扩大到全部列表：图纸上限 500、齐套上限 300，均先在数据库筛选，桌面端已有截断提示。分页完整性要按页面处理。

建议：接入真实分页，或至少明确提示截断及筛选方式，手机提供继续读取入口。

依据：[采购服务](../server/services/purchases/purchases.ts)、[采购页面](../app/pages/purchases.vue)、[手机到货列表](../app/pages/m/arrivals.vue)、[图纸页面](../app/pages/drawings.vue)、[齐套页面](../app/pages/kitting.vue)。

### F09 / P2：上传后放弃提交，没有通用孤儿文件清理

```ts

```

文件与上传记录先保存，创建异常或发放单时再绑定。取消、刷新或后续提交失败后，未绑定文件仍保留。仓库只发现演示清理，没有面向普通未绑定上传的过期策略；不据此推断部署端不存在额外运维脚本。

建议：规定未绑定上传有效期，清理时重新核验未绑定状态，避免与提交竞争。删除原报告未经本轮核实的磁盘占用数字。

依据：[上传保存](../server/services/issues/uploads.ts)、[异常绑定](../server/services/issues/issues.ts)、[附件绑定](../server/services/releases/releases.ts)、[演示清理](../server/services/dev/demo.ts)。

手机到货列表只消费数据和加载状态，没有区分请求错误。首次失败可落到默认空数组，显示“没有未到货的关键物料”。此项为源码确认，未做浏览器断网或错误注入。

## 三、条件性风险：保护缺口已确认，运行触发待验证

### R01 / P1：工序编辑使用锁前状态，存在并发覆盖路径

```ts
const step = await tx.routeStep.findUnique({ where: { id: stepId } })
await lockPart(tx, step.partId)
```

加工方式校验使用锁前对象，最终更新只按 ID。可疑时序：A 读到 `PENDING`；B 完整提交发出事务；A 再取得工件锁，仍按旧对象允许修改，可能留下 `OUT + SELF` 或覆盖供应商。

部分交错会死锁，不代表所有交错均被阻止。上一轮内存时序模拟不能替代 MySQL；本次未核实部署隔离级别，不能推断所有隔离级别的结果。

建议：统一锁顺序，锁后读取用于校验的最新状态，或采用预期状态条件更新；在专用库控制事务交错验证。

依据：[工序编辑及工件锁](../server/services/flow/steps.ts)、[发出事务](../server/services/flow/flow.ts)。

### R02 / P2：导入在事务外查重，存在并发重复插入路径

```ts
const { lines, errors } = validateRows(rows, ...)
await purchaseTx(async (tx) => { ... })
```

已有记录查询、重复校验发生在事务外。两个请求可能都得到无重复结果后分别插入。即使锁同一工件，后执行者锁后不重查；未关联工件时没有工件锁。

仓库模型及迁移没有对应导入业务键的唯一约束，`qmsInspectionId` 唯一键不能阻止普通导入重复。此前内存模拟支持该路径，但未真实 MySQL 复现，也未核查实库额外约束。

建议：明确导入幂等规则，再做事务内复核或适用的唯一约束；补并发同文件导入测试，不只测顺序重传。

依据：[导入校验及事务](../server/services/purchases/import.ts)、[模型](../prisma/schema.prisma)、[采购迁移](../prisma/migrations/20261020090000_r10_procurement/migration.sql)。

### R03 / P1：同步租约到期后，旧执行者仍有提交能力

```ts
const LEASE_MS = 15 * 60_000
```

```ts
return { skipped: false, value: await fn() }
```

租约固定 15 分钟，无执行中续租、失锁取消、提交持有权校验。资源写入不比较源版本，游标更新不比较旧游标。释放锁时检查持有人只能防误释放，不能阻止旧执行者提交。

触发条件：旧任务超过租期仍存活、第二执行者取得租约、旧页后提交，此时存在旧数据覆盖及游标回退路径。单请求 15 秒超时不能限制整轮 7 类资源、每类最多 200 页的总耗时。

此前沙箱模拟不代表实际部署已双跑。本次未确认执行者数量、真实超时重叠、回退事件或实库并发结果。

建议：续租与失锁退出配套，提交时校验持有权或版本，或采用有明确执行上限及写入隔离的批次机制。

依据：[同步租期](../server/services/sync/job.ts)、[租约](../server/services/jobs/lease.ts)、[资源写入](../server/services/sync/resources.ts)、[游标事务](../server/services/sync/sync.ts)、[请求超时](../server/services/sync/client.ts)。

### R04 / P2：SSR 异常详情内部请求未转发当前身份

```ts
useAsyncData('issue-detail', () => $fetch(...))
```

此片段省略类型与参数。桌面抽屉、手机异常详情在 `useAsyncData` 中直接调用全局 `$fetch`，未限定客户端执行，当前配置未关闭 SSR。本地 Nuxt 实现中，`useFetch` 的服务端本地请求改用 `useRequestFetch`，此处没有该处理。

直接打开带 ID 的详情地址，内部请求缺少页面会话 Cookie，存在被认证拒绝且页面未正确展示错误的路径。浏览器内点击的同源请求不会因此自动丢 Cookie；不是身份泄露或必然循环登录。源码与本地依赖已核验，未做真实浏览器直达、刷新验证。

建议：使用请求级 fetch 或合适的 `useFetch`，处理错误与重试，分别验证直达、刷新、客户端切换。

依据：[桌面异常详情](../app/components/IssueDrawer.vue)、[手机异常详情](../app/pages/m/issues.vue)、[SSR 配置](../nuxt.config.ts)、[认证](../server/middleware/auth.ts)。

## 四、性能与规模风险

以下是查询、计算结构事实，不是生产耗时结论。没有执行真实查询计划、负载或浏览器性能测试。

### P01 / P2：待匹配列表按工单串行查询

```ts
for (const wo of new Set(inspections.flatMap((i) => inspectionWorkOrders(i)))) {
  live.set(wo, (await activeOutsourceSteps(prisma, [wo])).map(toView))
}
```

每工单查工序，再查工序、供应商名称。此前实际服务内存计数为：1 个工单 6 次、10 个 33 次、100 个 303 次 Prisma 读取调用。计数依赖模拟数据中名称查询非空，不是真实 SQL 数或耗时；逐个 `await` 还会累计延迟。

建议批量查询相关工单后分组，以真实查询日志验证改善。

依据：[待匹配查询](../server/services/flow/match.ts)、[名称查询](../server/services/flow/names.ts)。

### P02 / P2：预警列表重新收集全局目标，范围过滤过晚

```ts
await collectTargets(at, thresholds, offDays, filter.rule)
```

先读活动预警、收集目标，最后在内存按工单和可见范围过滤。只看少量工单也可能触发全局读取、计算，多用户访问时与后台扫描叠加。

建议先下推工单与目标范围，减少重新扫描，再根据测量决定是否缓存，不把加缓存当作默认答案。

依据：[预警列表](../server/services/alerts/reminders.ts)、[目标收集](../server/services/alerts/scan.ts)。

### P03 / P2：看板按工单反复遍历整批数据

```ts
const out = outSteps.filter((s) => s.part.workOrderNumber === wo)
const open = issues.filter((i) => i.workOrderNumber === wo)
const mine = alerts.filter((a) => alertWo.get(a.id) === wo)
```

上述逻辑位于工单循环，计算量随“工单数 × 工序、异常、预警数”增长；部分预警读取未先限制范围。`Promise.all` 只能重叠读取，不能消除重复遍历。

建议预先按工单建 Map 或数据库聚合。权限解析的用户、项目经理查询是否需要索引，也须以真实查询计划判断，不能仅凭模型宣称已发生慢查询。

### 构建体积应如何解释

此前生产构建总产物约 13 MB，gzip 约 3.16 MB，属于服务端部署产物，不能当作首屏体积。全部路由 JS/CSS 合计约 1.89 MB，逐文件 gzip 合计约 666 KB，也不是首屏下载量或真实传输测量。

没有桌面、手机分别验证的网络瀑布、首屏加载和交互指标，不能据这些数字宣布页面慢或性能达标。

## 五、架构、工程及文档改进

### E01：保留模块化单体，收拢跨模块状态职责

```ts
import { lockParts, purchaseTx, refreshPartReady } from '../purchases/purchases'
```

图纸依赖采购提供工件锁、事务约定及就绪刷新，发放又依赖图纸状态收敛。工件就绪是跨业务约束，附着在采购服务会放大修改影响，F02 也说明跨模块状态需要明确责任方。

建议集中工件就绪及锁定约定，而不是堆入无边界工具目录。跨模块看板宜作查询层，不继续扩充异常变更服务；BOM 静态依赖演示编排也可收窄方向。

显式相对 TS/Vue 导入图未发现文件级循环，检查不含 Nuxt 自动导入；不能宣布完全无循环，也不能把模块双向业务依赖直接叫循环引用。文件长本身不是缺陷，拆分应减少真实耦合。

依据：[图纸依赖](../server/services/drawings/drawings.ts)、[发放依赖](../server/services/releases/releases.ts)、[看板](../server/services/issues/board.ts)、[BOM 来源](../server/services/bom/source.ts)。
