# 发版手册

本仓库的 GitHub 发版流程。部署目标、首次上线步骤和回滚细节见 [上线手册.md](上线手册.md) 第 5 节；本文只讲"从代码到 tag"这一段。

## 链路

```text
功能分支
  -> PR 标题校验（.github/workflows/pr-title.yml）
  -> CI 全绿（.github/workflows/ci.yml：typecheck / 单元测试 / 构建）
  -> squash 合并到 main（main 上只留 PR 标题这一条 commit）
  -> release-please 自动开/更新发布 PR（.github/workflows/release-please.yml）
  -> 合并发布 PR
  -> 自动打 tag fulfillment-vX.Y.Z
  -> deploy workflow（.github/workflows/deploy.yml）SSH 到 ECS 执行 scripts/deploy-remote.sh
  -> 健康检查通过才算发布完成
```

发布分两次合并：先合功能 PR（代码进 main），再合发布 PR（定版本、打 tag、部署）。

## 提交与 PR 标题格式

Conventional Commits，`type` 必须是下列之一：

```text
feat     新功能        -> minor（0.1.0 -> 0.2.0）
fix      修缺陷        -> patch
perf     性能          -> patch
refactor 重构          -> 不发版
docs     文档          -> 不发版
test     测试          -> 不发版
build    构建/依赖     -> 不发版
ci       CI 配置       -> 不发版
chore    杂项          -> 不发版
revert   ﻿回滚          -> patch
```

scope 可选，描述可以用中文：

```text
feat(plan): 节点确认后自动推进下一步
fix(purchases): 撤销到货后未回滚承诺日
ci(actions): 添加发版工作流
```

破坏性变更写 `feat(api)!: ...`，或在正文加 `BREAKING CHANGE: ...`，会升 major。当前版本在 `0.x`，按 release-please 默认规则，破坏性变更同样升 major（`0.3.1 -> 1.0.0`）；不想这么早进 1.0 时在 `release-please-config.json` 打开 `bump-minor-pre-major`。

**只有 PR 标题被校验。** 分支里的中间 commit 怎么写都行，squash 之后不会进 main。

## 仓库设置（一次性）

1. **合并方式**只留 squash，并强制用 PR 标题作为 commit 标题：

   ```bash
   gh api -X PATCH repos/ajie5419/Fulfillment-Tracker \
     -f allow_merge_commit=false -f allow_rebase_merge=false \
     -f allow_squash_merge=true \
     -f squash_merge_commit_title=PR_TITLE \
     -f squash_merge_commit_message=PR_BODY
   ```

   `squash_merge_commit_title` 必须是 `PR_TITLE`。默认的 `COMMIT_OR_PR_TITLE` 在"PR 只有一个 commit"时会改用那个 commit 的标题，等于绕开校验。

2. **Secrets**（Settings → Secrets and variables → Actions）：

   | 名称 | 说明 |
   |---|---|
   | `RELEASE_PLEASE_TOKEN` | 推荐：细粒度 PAT，权限 `Contents: read/write`、`Pull requests: read/write`。不配也能跑（退回 `GITHUB_TOKEN`），但 `GITHUB_TOKEN` 创建的发布 PR 不会触发 CI，需要手动关掉再 reopen 一次 |
   | `DEPLOY_HOST` | ECS 公网 IP |
   | `DEPLOY_USER` | SSH 用户，需能执行 docker 且对 `/opt/fulfillment` 有写权限 |
   | `DEPLOY_SSH_KEY` | 该用户的私钥（OpenSSH 格式，含首尾行） |
   | `DEPLOY_PORT` | 可选，默认 22 |

3. **分支保护**（Settings → Branches → `main`）：

   - Require a pull request before merging
   - Require status checks to pass：勾 `Validate PR title`、`Check`
   - Require branches to be up to date before merging

   **顺序**：先合并本文和 workflow 到 main，再配 status check，最后关掉 merge commit。反过来会把老 PR 锁死（它们没有这些 check，永远无法合并）。

## 日常发版

```bash
git switch main && git pull --ff-only
git switch -c feat/<scope>

# 改代码、补测试、更新文档
git commit -m "feat(<scope>): ..."      # 中间 commit 格式不限
git push -u origin feat/<scope>
gh pr create --base main --head feat/<scope> --title "feat(<scope>): ..."

gh pr checks <PR编号> --watch            # 等 PR Title 和 CI 绿
gh pr merge <PR编号> --squash --delete-branch
```

合并后 release-please 会在几分钟内开一个标题为 `chore(main): release fulfillment x.y.z` 的 PR，只改 `CHANGELOG.md` 和 `.release-please-manifest.json`。等它的检查绿了再合并：

```bash
gh pr checks <发布PR编号> --watch
gh pr merge <发布PR编号> --squash --delete-branch
```

合并发布 PR 后 release-please 打 `fulfillment-vX.Y.Z` tag，deploy workflow 自动开始部署：

```bash
gh run list --workflow deploy.yml --limit 5
gh run watch <run-id>                    # 结论必须 success
```

## 判断是否发布完成

四条同时满足才算：

- 发布 PR 已合并
- tag 形如 `fulfillment-v*` 已生成（`git fetch --tags && git tag -l 'fulfillment-v*'`）
- deploy workflow 结论 `success`
- ECS 上 `curl -s http://127.0.0.1:3100/api/health` 返回 `{"ok":true}`

只有 GitHub Release 或只有 tag，都不代表生产已更新。

## 发布失败

- **PR 标题校验失败**：改标题即可，重新打开/编辑会自动重跑。找不到该 check 时确认 workflow 已在 main 上。
- **CI 失败**：修代码，push 到同一分支，check 会重跑。
- **deploy 失败**：
  - `Preflight` 报缺 Secrets：按上表补齐。
  - SSH 连不上：确认安全组放行、`DEPLOY_SSH_KEY` 是私钥且公钥在 ECS 的 `~/.ssh/authorized_keys`。
  - 迁移或构建失败：脚本在启动前退出，旧版本仍在跑。
  - 健康检查超时：脚本自动把 `fulfillment-tracker:prev` 打回 `latest` 并 `up -d`，回退后退出非 0。日志里会有 `--tail 80` 和应用日志，按 [上线手册.md](上线手册.md) 5.6 处理；带迁移的版本要先评估旧版本能否在新表结构上运行。
- **重试部署**：在 Actions 页面 Re-run failed jobs，或手动 `git tag -f` 后推送同一 tag（不推荐）。重跑前先确认上一次失败原因。

## 第一次启用时的注意

- `bootstrap-sha` 固定在 `3fdc1e5`（本仓库加入发版流程前的最后一个 commit）。release-please 只统计它之后的 commit，历史里那些 `R14 评审修复：...` 之类的标题不会被误解析；等第一次发布 PR 合并后这一行可以删掉。
- `.release-please-manifest.json` 初始是 `0.0.0`，配合 `initial-version: 0.1.0`，首次发布是 `0.1.0`，不是 `1.0.0`。release-please 对"没有历史 release 且 manifest 为 0.0.0"的包会直接跳到 `1.0.0`，`initial-version` 用来覆盖这个默认值。
- `release-type` 用 `simple`（只维护 `CHANGELOG.md` 和 manifest），不用 `node`：本仓库不是 npm 包，`package.json` 没有 `version` 字段，`node` 类型会往里塞一个没人读的版本号。
